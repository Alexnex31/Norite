# ADR 0022: HS256 access tokens, and scopes that only ever restrict

## Status
Accepted. Refines [ADR 0011](0011-token-based-client-auth.md), which established token-based client auth
and that `api_tokens` carry scopes, but left the signing algorithm and the scope semantics open. Depends on
[ADR 0023](0023-voice-connection-authentication.md) for the reasoning that keeps the access token
in-process — the two were decided together.

## Context
Milestone M4 has to sign access tokens and decide what a scope actually means. Both are expensive to change
later: the algorithm fixes the token format, and scope semantics become the security model every future
endpoint is written against.

The tempting instinct is to reach for an asymmetric algorithm on the grounds that it is "more secure." It is
not — HS256 (HMAC-SHA256) and Ed25519 both sit at roughly 128-bit security with no practical attack against
either. What asymmetric buys is **key separation**: the ability to let something verify a token without also
being able to mint one. That is worth paying for exactly when a component outside the signer needs to
verify, and worth nothing when it does not.

The candidate for such a component was the SFU, which the flagship runs as separate, internet-exposed,
privileged pods (ADR 0021). Working that through produced ADR 0023, whose conclusion is that **the access
token is never presented to the media server at all** — the SFU authenticates connections through WebRTC's
own DTLS fingerprint binding, with no bearer token anywhere in the flow. That removes the only prospective
external verifier, and with it the case for asymmetric signing.

## Decision

**Access tokens are signed with HS256**, using a single 32-byte secret from `[auth].jwt_secret`, generated by
`norite instance init` and overridable by `NORITE_JWT_SECRET` for the flagship's Kubernetes Secret. The
algorithm is pinned at verification, so a token whose header claims `none` or any other family is rejected
before its signature is considered.

**The signing key never leaves the backend.** Nothing else verifies an access token: the gateway is
in-process, the SFU uses fingerprint binding (ADR 0023), and the daemon *holds* tokens rather than verifying
them. Any future requirement for an external verifier is a trigger to revisit this decision, not to
distribute the key.

**Scopes only ever restrict.** They exist to bound a *delegated* credential below what its owner can already
do; they never grant. A user's own access token passes every scope check, because a scope system that must
enumerate what a person may do would silently lock people out of each new feature until someone remembered
to add it. Permission resolution still runs on top of every scope check — a scope is a ceiling, never a
floor (CLAUDE.md rule 1).

**Token management is not delegable.** Minting, listing and revoking `api_tokens` all require a *user* actor
and have no scope at all. Minting because a token that can mint tokens can grant itself scopes it does not
hold, which would make every other restriction decorative. Listing because it discloses the names, scopes and
last-use times of the account's other tokens — reconnaissance for a compromised low-privilege bot, with no
delegation use case worth it.

**Unknown scopes are rejected at mint time**, never dropped. Silently dropping one hands back a token weaker
than the caller believes; silently keeping one would let a later release that *does* understand the string
widen an existing token's reach without anyone re-approving it.

## Consequences

- Verification is ~5.6µs and needs no database round trip, which is what keeps `Authenticate` cheap enough to
  run on every request. Measured against the same machine's Postgres: a trivial `SELECT 1` is 48µs, so token
  verification is an order of magnitude below the cheapest thing a handler can do.
- Rotating the signing key invalidates outstanding access tokens but **not** refresh tokens, which are opaque
  database rows. Clients recover on their next refresh without re-authenticating, so the blast radius of a
  rotation is one 15-minute TTL and no user-visible event.
- Migrating to an asymmetric algorithm later is correspondingly cheap: verify both, sign the new one, drop
  the old after the TTL elapses. This decision is reversible in two deploys, which is part of why it is
  defensible now.
- HS256 is **more** quantum-resistant than the asymmetric alternatives, not less: Grover's algorithm only
  halves the effective security of a 256-bit HMAC key, while Shor's breaks elliptic-curve signatures
  outright. Irrelevant on any near-term horizon, and the industry will migrate together when it is not, but
  it means "asymmetric is more secure" would have been the wrong sentence to write down.
- The scope vocabulary is deliberately tiny at M4 (`identify` alone). It grows with the surface it guards;
  each milestone that adds an endpoint an API token should reach adds the scope for it, rather than scope
  strings being invented at a call site where a typo widens access.

## Alternatives considered

- **EdDSA (Ed25519)**: the serious contender, and the one this ADR spent the most time on. Verifiers cannot
  mint, and the public key could later back a JWKS endpoint. Rejected because ADR 0023 removed the only
  external verifier: with nothing outside the backend verifying, key separation protects against nothing,
  and the cost is real — ~35µs per verify instead of ~5.6µs, on the one auth path that otherwise touches no
  database. Ed25519's private key derives from a 32-byte seed, so the config shape would have been
  unchanged; the decision turned entirely on whether an external verifier exists.
- **RS256**: rejected outright. 578µs to sign, 462-byte tokens against HS256's 163, and no advantage over
  EdDSA for any purpose here.
- **A shared key for both access tokens and a future voice credential**: rejected in favour of separate keys
  per purpose. Even where a voice credential is eventually signed (ADR 0023 leaves that open), it gets its own
  key, so compromise of the voice key cannot mint access tokens.
- **Scope-gated token management (`tokens:read` / `tokens:write`)**: implemented first, then removed. A
  delegated credential that can enumerate or create credentials undermines the model it is part of, and the
  convenience of a bot rotating its own token does not pay for that.
- **Granting user access tokens every scope explicitly**, rather than treating a user actor as unrestricted:
  rejected — a new scope would then lock human users out of a feature until someone updated the implicit set,
  which is a failure mode that appears in production rather than in review.
